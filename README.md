# Frogster

Защищённый мессенджер со сквозным шифрованием. Бэкенд — микросервис на Go,
клиент — единое Flutter-приложение под Windows, Linux, macOS, Android и iOS.

Сервер спроектирован как **маршрутизатор шифротекста**: он хранит и раздаёт
публичные ключи, ставит сообщения в очередь для офлайн-получателей и разносит
их по WebSocket, но не имеет ни одного кодового пути, способного расшифровать
тело сообщения.

## Быстрый старт

```bash
# 1. Инфраструктура (PostgreSQL + Redis)
docker compose -f deploy/docker-compose.yml up -d

# 2. Миграции
cd server && go run ./cmd/migrate up

# 3. Сервер сообщений и сервер вложений
#    Порты 18080/18081 вместо 8080/8081: Windows резервирует 8029-8128.
FROGSTER_ENV=dev FROGSTER_REDIS_URL=redis://localhost:16379/0 FROGSTER_ADDR=0.0.0.0:18080 go run ./cmd/frogsterd

FROGSTER_ENV=dev FROGSTER_REDIS_URL=redis://localhost:16379/0 FROGSTER_FILED_ADDR=0.0.0.0:18081 go run ./cmd/filed

# 4. Клиент. Для телефона подставьте IP компьютера вместо 127.0.0.1
#    (узнать: ipconfig -> IPv4 вашего Wi-Fi адаптера).
cd ../client
flutter run --dart-define=FROGSTER_SERVER=http://192.168.1.42:18080 --dart-define=FROGSTER_FILE_HOST=192.168.1.42 --dart-define=FROGSTER_FILE_PORT=18081

# 5. Проверка
cd ../server && go test ./... -race
python testdata/e2e_test.py         # сообщения, офлайн-очередь, rate limiting
python testdata/multidevice_test.py # уведомления о смене ключей
python testdata/fanout_test.py      # per-device шифротекст
# (требует: pip install websocket-client)
```

Rate-limiting держит состояние в Redis между рестартами. Если E2E-скрипты
упираются в 429, сбросьте бакеты:

```bash
docker compose -f deploy/docker-compose.yml exec redis \
  redis-cli EVAL "local ks=redis.call('keys','frogster:rl:*'); for i=1,#ks do redis.call('del',ks[i]) end; return #ks" 0
```

## API

| Метод | Путь | Аутентификация | Назначение |
|---|---|---|---|
| POST | `/v1/register` | нет | регистрация + загрузка публичных ключей |
| POST | `/v1/login` | нет | вход, выдача токенов |
| GET | `/v1/keys/{username}` | да | X3DH-бандл (расходует one-time prekey) |
| GET | `/v1/keys/count` | да | глубина пула prekey |
| POST | `/v1/keys` | да | пополнение пула |
| POST | `/v1/chats` | да | создание чата |
| GET | `/v1/sessions` | да | активные сессии |
| DELETE | `/v1/sessions/{id}` | да | отзыв сессии |
| GET | `/v1/ws` | да (subprotocol) | WebSocket |

gRPC (`:8081` по умолчанию, `FROGSTER_FILED_ADDR`; `proto/frogster/v1/file.proto`): `Upload` (стрим),
`Download` (стрим), `Delete`. Аутентификация — тот же bearer-токен в
метаданных, через unary- и stream-интерсепторы.

Токен для WebSocket передаётся в `Sec-WebSocket-Protocol` как
`frogster.bearer.<token>` — в query-строке он утекал бы в логи доступа.

## Как устроено шифрование

Коротко: **X3DH + Double Ratchet**, тот же протокол, что у Signal и WhatsApp.
Реализован в этом проекте, а не взят готовым — все зрелые Dart-порты Signal
Protocol под GPL/AGPL, что несовместимо с App Store
([ADR 0001](docs/adr/0001-crypto-library-choice.md)).

Написан **только протокольный слой**. Сами примитивы взяты из `cryptography`
2.9.0 (Apache-2.0) поверх `pointycastle` (MIT):

| Назначение | Алгоритм |
|---|---|
| Обмен ключами | X25519 (Curve25519) |
| Подписи | Ed25519 |
| Вывод ключей | HKDF-SHA256 |
| Цепочка ключей | HMAC-SHA256 |
| Шифрование сообщения | AES-256-GCM |
| Отпечаток (safety number) | SHA-512, 5200 итераций |

Отдельно от E2EE-контура: пароли — bcrypt (cost 12), JWT — HS256, вложения —
AES-256-GCM чанками по 64 КиБ.

### Что происходит при отправке сообщения

**1. Установка сессии (X3DH).** Alice берёт с сервера бандл Bob: identity-ключ,
подписанный prekey и один одноразовый prekey. Проверяет подпись, генерирует
эфемерную пару и считает четыре Diffie-Hellman:

```
DH1 = DH(IK_A,  SPK_B)      аутентифицирует Alice
DH2 = DH(EK_A,  IK_B)       аутентифицирует Bob
DH3 = DH(EK_A,  SPK_B)      forward secrecy
DH4 = DH(EK_A,  OPK_B)      опционально, усиливает FS первого сообщения
SK  = HKDF-SHA256(0xFF*32 || DH1 || DH2 || DH3 || DH4, info="Frogster_X3DH_...")
```

Смысл схемы — Bob может быть **офлайн**. Его ключи лежат на сервере заранее,
поэтому первое сообщение шифруется без единого раунда с ним.

Одноразовый prekey выдаётся **атомарно** (`FOR UPDATE SKIP LOCKED`): выдай
сервер один ключ двоим — forward secrecy, ради которой prekey существует, была
бы аннулирована.

**2. Ключ на каждое сообщение (Double Ratchet).** Общий секрет — это только
начало. Дальше каждое сообщение получает собственный ключ:

```
message_key    = HMAC-SHA256(chain_key, 0x01)
next_chain_key = HMAC-SHA256(chain_key, 0x02)
```

Функция односторонняя, а `message_key` **стирается сразу после расшифровки**.
Захват телефона сегодня не раскрывает вчерашнюю переписку — ключей уже нет.
Это forward secrecy.

При смене направления диалога добавляется DH-рэтчет: новая пара ключей и два
вывода корневого ключа. Даже полная компрометация состояния перестаёт помогать
атакующему через несколько сообщений — post-compromise security.

> Константы `0x01` и `0x02` обязаны различаться. Сделай их одинаковыми — всё
> продолжит работать, но утечка одного ключа раскроет всю цепочку вперёд. Это
> проверяется отдельным тестом, потому что ни один функциональный тест такую
> поломку не увидит.

**3. Шифрование под каждое устройство.** У каждого устройства свой рэтчет,
поэтому сообщение шифруется **отдельно** для каждого устройства собеседника и
для остальных своих (так работает синхронизация между телефоном и ПК). Сервер
раздаёт каждому устройству его payload.

**4. Отправка.** Сервер получает набор байтов, идентификаторы и размеры. Больше
ничего.

### Почему сервер не может прочитать переписку

Не потому, что «мы так не делаем» — потому, что **у него нет ключей**.
Приватные ключи (identity, prekey, состояние рэтчета) лежат в keychain
устройства и никогда не покидают его.

Защита от случайной утечки в логи — структурная: `Envelope`, `Message`,
`MessageDelivery` и `GroupSenderKeyDistribution` реализуют `slog.LogValuer` и
возвращают только идентификаторы и размеры. Даже
`slog.Info("frame", "env", env)` физически не может напечатать шифротекст.
Тесты ищут секрет в raw, base64 (std/raw/url) и hex.

Проверить лично — [TESTING.md](TESTING.md), часть 9: залезть в базу и логи и
поискать там своё сообщение.

### Слабое место: сервер раздаёт ключи

Сервер не доказывает, что публичный ключ принадлежит заявленному владельцу —
это заявленная модель доверия. Вредоносный сервер мог бы подсунуть свой ключ и
встать посередине.

Защита — **TOFU**: identity-ключ пиннится при первом контакте, а его изменение
всегда показывается пользователю. Плюс 60-значный safety number для сверки по
внешнему каналу (голосом, при встрече) — если цифры совпали, посредника нет.

### Смена телефона

Приватный ключ привязан к устройству, иначе он не был бы device-bound. Значит
новый телефон = новый identity-ключ, и это **штатное событие**, а не атака.

По умолчанию (`TrustPolicy.notifyAndReestablish`, как в WhatsApp и Signal)
сессия пересоздаётся автоматически, отправка продолжает работать, пользователь
видит информационную плашку. Доступен строгий режим `TrustPolicy.strict` —
отправка блокируется до сверки safety number.

Размен осознанный: блокировать каждую смену ключа значит сделать обычное
обновление телефона неотличимым от атаки и приучить игнорировать
предупреждение — то самое, которое однажды окажется настоящим. Обратная сторона
честная: под политикой по умолчанию MITM со стороны сервера виден только как
плашка, которую можно пролистать.

Старая переписка на новое устройство **не переносится** — её ключи остались на
старом. Это следствие forward secrecy, а не недоработка.

### Группы

Шифровать групповое сообщение отдельно каждому устройству — O(N) операций с
открытым ключом. Sender keys сводят это к одному симметричному шифрованию:
отправитель раздаёт цепочку один раз через попарные сессии, дальше рассылает
один шифротекст.

Каждое сообщение **подписывается** Ed25519: симметричный ключ общий, поэтому
AEAD доказывает лишь членство в группе, но не авторство.

Критичный инвариант — **ротация по эпохам**. Вышедший участник сохранил копии
всех полученных ключей, поэтому при любом изменении состава эпоха
инкрементируется, старые SKDM удаляются из БД, все выпускают новые ключи. Без
этого удалённый читал бы группу вечно.

### Насколько этому можно верить

Функциональные тесты не доказывают безопасность рэтчета: ошибка в нём **не
ломает доставку**. Сообщения ходят, тесты зелёные, forward secrecy нет.

Поэтому в код вносились 16 намеренных поломок и проверялось, ловят ли их тесты.
**6 изначально прошли незамеченными** — включая `message_key == next_chain_key`,
тихо убивающий forward secrecy. После этого тесты были усилены; сейчас ловятся
все 16. Таблица — в [docs/crypto-protocol.md](docs/crypto-protocol.md).

Один тест обнаружил и настоящий баг: проверка подписи стояла **до** проверки
границы пропуска, так что легитимный участник группы мог заставить вывести
произвольное число ключей. Порядок исправлен.

**Криптослой не проходил внешний аудит.** Мутационное тестирование повышает
уверенность, но самописный ratchet перед продакшеном нужно аудировать.

Полное описание протокола, форматы сообщений и границы —
[docs/crypto-protocol.md](docs/crypto-protocol.md).

## Гарантии безопасности

**Никакого plaintext на сервере.** Защита структурная, а не дисциплинарная:
`Envelope`, `Message`, `MessageDelivery` и `GroupSenderKeyDistribution`
реализуют `slog.LogValuer`, возвращая только идентификаторы и размеры. Даже
`slog.Info("frame", "env", env)` физически не может напечатать шифротекст.
Покрыто тестами в [server/internal/ws/redaction_test.go](server/internal/ws/redaction_test.go),
которые ищут секрет в raw, base64 (std/raw/url) и hex.

**Атомарная выдача one-time prekey.** Реализовано через
`FOR UPDATE SKIP LOCKED`, проверено конкурентным тестом.

**Rate limiting.** Token bucket на Lua внутри Redis (атомарный, общий для
инстансов). IP-лимит стоит до аутентификации, user-лимит — после.

**Сервер не проверяет владение приватным ключом.** Это заявленная модель
доверия. Клиент пиннит identity-ключ при первом контакте, сообщает о любой его
смене и показывает 60-значный safety number для сверки по внешнему каналу.
Реакция на смену задаётся `TrustPolicy` — см. «Смена телефона» выше.

**Отзыв устройства.** `DELETE /v1/sessions/{id}` отзывает сессию **и помечает
устройство** `revoked_at` в одной транзакции. Отзыв только сессии оставил бы
устройство в выдаче ключей: контакты продолжали бы шифровать на утерянный
телефон, и сообщения молча уходили бы в никуда.

**Forward secrecy.** Каждое сообщение шифруется своим ключом, который
уничтожается сразу после использования. Приватные ключи (identity, prekey,
состояние рэтчета) не покидают устройство.

**Ротация ключей группы.** Любое изменение состава инкрементирует эпоху чата;
удалённый участник теряет доступ, а старые sender key удаляются из БД. Сервер
делает это в одной транзакции с изменением членства и отвергает SKDM со старой
эпохой.

**Вложения.** Файл шифруется на устройстве (AES-256-GCM, свой ключ на каждый
файл) до отправки первого байта; ключ едет получателям внутри Double Ratchet.
Сервер хранит блобы, которые не может прочитать, и не знает ни имени файла, ни
типа: при загрузке объявляется обобщённый `content_hint`, а настоящий MIME-тип
лежит в зашифрованном payload. Целостность — SHA-256, проверяется **до**
расшифровки. Вложения скачиваются только по явному действию пользователя:
автозагрузка тратила бы мобильный трафик и показывала бы наблюдателю, в каких
именно сообщениях были файлы.

**Миграции локальной БД сохраняют состояние.** Схема обновляется через
`ALTER TABLE`, а не пересозданием: потеря `ratchet_sessions` сделала бы все
прошлые переписки нерасшифровываемыми навсегда. Проверено тестом, который
падает на «drop and recreate» варианте.

**Верификация мутациями.** 16 намеренных поломок, 6 изначально прошли все
тесты — см. «Насколько этому можно верить» выше.

## Известные ограничения

- **Метаданные.** Сервер видит социальный граф, тайминги и размеры сообщений.
  Это принятая утечка данной архитектуры.
- **Сборка под Windows** требует трёх вещей, и `flutter doctor` показывает не
  все сразу:
  1. **Developer Mode** (`start ms-settings:developers`) — иначе падает на
     symlink-зависимостях плагинов;
  2. **ATL** (`Microsoft.VisualStudio.Component.VC.ATL`) — нужен
     `flutter_secure_storage_windows`, ошибка `atlstr.h: No such file`;
  3. **C++ CMake tools for Windows** — без него `Unable to find suitable
     Visual Studio toolchain`.

  Отдельно: если в `VC\Tools\MSVC` окажется версия **без** `cl.exe` (бывает
  после прерванной установки), её нужно удалить. Flutter всегда берёт старшую
  версию и упирается в пустой каталог — ошибка выглядит как
  `Building native assets failed`, что на настоящую причину не указывает.
  **`flutter build apk` от всего этого не зависит.**

- **Порты 6379, 8080, 8081 могут быть недоступны на Windows.** Hyper-V/WSL
  резервируют диапазоны портов, и Docker не может привязаться внутри них, даже
  когда никто не слушает. Проверить: `netsh interface ipv4 show
  excludedportrange protocol=tcp`. Поэтому по умолчанию Redis публикуется на
  **16379**, а серверы удобно запускать на **18080/18081**.
- **Вложения — только изображения.** `file_picker` 11 не мигрировал на
  встроенный Kotlin во Flutter 3.44 и ломает сборку Android
  (`GeneratedPluginRegistrant: cannot find symbol`); исправление есть только в
  бете 12.0.0. Используется `image_picker` (поддерживается командой Flutter).
  Пикер внедряется в `ChatScreen` через колбэк, поэтому замена на произвольные
  файлы затрагивает один метод в `app.dart`.
- **`kotlin.incremental=false`** в `android/gradle.properties` — обход
  Windows-бага, когда демон Kotlin держит блокировку на своих `.tab`-кэшах.
- **Локальная БД хранит расшифрованные сообщения.** Это осознанный компромисс
  ради офлайн-режима: устройство — единственное место, где plaintext допустим,
  и его защищает шифрование диска и блокировка экрана. Ключи там не лежат —
  они в keychain платформы.
- **Криптослой не проходил внешний аудит.** Мутационное тестирование повышает
  уверенность, но самописный ratchet перед продакшеном нужно аудировать.
