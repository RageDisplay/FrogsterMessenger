# Криптографический протокол Frogster

Реализация: `client/lib/crypto/`. Спецификации — Signal
[X3DH](https://signal.org/docs/specifications/x3dh/) и
[Double Ratchet](https://signal.org/docs/specifications/doubleratchet/).

## Примитивы

Ни один примитив не написан в этом проекте. Всё берётся из `cryptography`
2.9.0 (Apache-2.0), который внутри опирается на `pointycastle` (MIT).

| Назначение | Алгоритм |
|---|---|
| Diffie-Hellman | X25519 |
| Подписи | Ed25519 |
| KDF | HKDF-SHA256 |
| Цепочка ключей | HMAC-SHA256 |
| Шифрование сообщения | AES-256-GCM |
| Отпечатки (safety number) | SHA-512, 5200 итераций |

## Ключи устройства

Устройство держит **две** identity-пары. Curve25519 не умеет подписывать,
Ed25519 не умеет DH; Signal решает это через XEdDSA, но для этого нужна
арифметика кривой Эдвардса, которой нет в поддерживаемых permissive-пакетах
Dart (см. [ADR 0002](adr/0002-identity-key-curve25519.md)).

| Ключ | Алгоритм | Приватная часть |
|---|---|---|
| Identity DH | Curve25519 | keychain, не покидает устройство |
| Identity signing | Ed25519 | keychain |
| Signed prekey | Curve25519 (подписан Ed25519) | keychain |
| One-time prekey | Curve25519 | keychain, **удаляется после использования** |

Публикуются только публичные половины. Тест
`the published bundle contains no private material` проверяет, что в
загружаемом бандле нет приватного материала.

## X3DH

```
проверить Sig(IK_B_ed25519, SPK_B)      -- при провале сессия не создаётся
сгенерировать эфемерный EK_A
DH1 = DH(IK_A,  SPK_B)      аутентифицирует Alice
DH2 = DH(EK_A,  IK_B)       аутентифицирует Bob
DH3 = DH(EK_A,  SPK_B)      forward secrecy
DH4 = DH(EK_A,  OPK_B)      опционально, усиливает FS первого сообщения
SK  = HKDF-SHA256(0xFF*32 || DH1||DH2||DH3||DH4, salt=0, info="Frogster_X3DH_...")
```

Отсутствие OPK — штатная ситуация (пул на сервере пуст), сессия создаётся без
DH4. Associated data сессии — `IK_A || IK_B`, всегда в порядке
инициатор→ответчик, аутентифицируется с каждым сообщением.

Роли зеркальны: где Alice берёт свой приватный ключ против публичного ключа
Bob, Bob берёт свой приватный против публичного Alice. Перепутанные пары дают
разные секреты — ловится тестом
`initiator and responder derive the same secret`.

## Double Ratchet

Симметричный рэтчет — один шаг на сообщение:

```
message_key    = HMAC-SHA256(chain_key, 0x01)
next_chain_key = HMAC-SHA256(chain_key, 0x02)
```

**Константы 0x01 и 0x02 обязаны различаться.** Если обе ветки вывести с одной
константой, сообщения продолжат шифроваться и расшифровываться нормально, но
любой утёкший message key раскроет всю оставшуюся цепочку. Это проверяется
напрямую в группе тестов `chain KDF one-way property`, потому что ни один
функциональный тест такую поломку не увидит (проверено мутацией).

DH-рэтчет при смене направления: два вывода корневого ключа, новая пара ключей
на отправку. Даёт post-compromise security.

Message key уничтожается сразу после использования (`wipe`). Именно это делает
прошлые сообщения нечитаемыми при захвате текущего состояния.

### Границы

| Параметр | Значение | Зачем |
|---|---|---|
| `maxSkip` | 1000 | Пир не может заставить вывести произвольное число ключей (DoS) |
| `maxSkippedKeysStored` | 2000 | Ограничение памяти под отложенные ключи |

Отложенный ключ **одноразовый**: он удаляется из хранилища при использовании,
иначе повтор сообщения расшифровывался бы бесконечно.

## Формат сообщения

```jsonc
// prekey-сообщение (ct=1): самодостаточно, Bob может быть офлайн
{ "ct":1, "body":"<base64>", "ik":"<base64>", "ek":"<base64>", "otp":57 }

// обычное (ct=2)
{ "ct":2, "body":"<base64>" }
```

`body` содержит заголовок рэтчета и AEAD-шифротекст. Заголовок передаётся как
associated data, поэтому подмена заголовка ломает аутентификацию.

Инициатор прикладывает handshake-материал к каждому сообщению, пока не получит
ответ: до этого момента неизвестно, дошло ли первое сообщение.

## TOFU и safety numbers

Сервер не доказывает принадлежность публичного ключа. Поэтому:

1. При первом контакте identity-ключ пира **пиннится**.
2. При изменении ключа поведение задаётся `TrustPolicy` (см. ниже).
3. Safety number — 60 цифр, одинаковых с обеих сторон (два отпечатка
   сортируются перед склейкой), для сверки по внешнему каналу.

Без пиннинга заявление об E2EE несостоятельно: вредоносный сервер подменил бы
ключ и читал переписку.

### Смена устройства и TrustPolicy

Приватный ключ привязан к устройству — иначе он не был бы device-bound. Значит
**новый телефон = новый identity-ключ**, и это штатное событие, а не аномалия.

| | `notifyAndReestablish` (по умолчанию) | `strict` |
|---|---|---|
| Сессия | пересоздаётся автоматически | не трогается |
| Отправка | продолжает работать | блокируется |
| Пользователь | информируется плашкой | обязан сверить safety number |

Размен осознанный. Блокировка на каждую смену ключа делает обычное обновление
телефона неотличимым от атаки и приучает игнорировать предупреждение — то
самое, которое однажды окажется настоящим. При этом MITM со стороны сервера
под политикой по умолчанию виден только как плашка, поэтому `strict` остаётся
доступной.

Инвариант: после автоматического пересоздания `acceptedChange` **сбрасывается
в false**. Иначе однократное согласие превратилось бы в бессрочное доверие и
следующая подмена прошла бы молча.

### Отзыв устройства

`DELETE /v1/sessions/{id}` отзывает сессию **и помечает устройство**
`revoked_at` в одной транзакции. Отзыв только сессии оставил бы устройство в
выдаче ключей: контакты продолжали бы шифровать на утерянный телефон, и
сообщения молча уходили бы в никуда.

## Групповые чаты — sender keys

Шифровать групповое сообщение отдельно каждому устройству — O(N) операций с
открытым ключом на сообщение. Sender keys сводят это к одному симметричному
шифрованию: отправитель раздаёт свою цепочку один раз через попарные сессии, а
дальше рассылает один шифротекст, который сервер разносит без изменений.

```
message_key    = HMAC-SHA256(chain_key, 0x01)
next_chain_key = HMAC-SHA256(chain_key, 0x02)
```

Каждое сообщение дополнительно **подписывается** ключом отправителя: у всех
членов группы один симметричный ключ, поэтому AEAD доказывает лишь членство в
группе, но не авторство. Без подписи любой участник мог бы выдать себя за
любого другого.

SKDM (раздача ключа) шифруется попарно в Double Ratchet — сервер видит только
байты. В SKDM **не входит** signing seed: иначе получатель мог бы подписывать
сообщения от имени отправителя.

### Ротация по эпохам — критичный инвариант

Вышедший участник сохраняет копии всех sender key, которые получал. Поэтому
при любом изменении состава чат переходит в новую эпоху:

| Событие | Действие |
|---|---|
| Участник добавлен | `epoch += 1`, все выпускают новые ключи |
| Участник удалён | `epoch += 1`, **старые SKDM удаляются из БД**, все выпускают новые ключи |

Сервер (`store/groups.go`) делает это в одной транзакции с изменением
членства, отвергает SKDM со старой эпохой (`ErrStaleEpoch`) и не отдаёт
устройствам ключи не текущей эпохи. Клиент
(`ratchet/sender_key.dart`) отказывается расшифровывать сообщение, эпоха
которого не совпадает с текущей.

Защита двухслойная: запрос выдачи джойнится по текущей эпохе **и** старые
строки физически удаляются. Тест проверяет оба слоя отдельно — иначе удаление
можно было бы убрать незаметно.

## Шифротекст на устройство

У каждого устройства свой Double Ratchet. Прямое сообщение поэтому шифруется
**отдельно для каждого устройства**:

```jsonc
{ "v":1, "type":"msg", "id":"…", "chat_id":"…",
  "payloads": [
    {"user_id":"…","device_id":"dev-1","ct_type":2,"ciphertext":"<base64>"},
    {"user_id":"…","device_id":"dev-2","ct_type":2,"ciphertext":"<base64>"}
  ] }
```

В набор входят устройства собеседника **и** остальные свои — именно это
синхронизирует отправленные сообщения между своими устройствами.

Сервер кладёт per-device шифротекст в `message_deliveries.ciphertext` и раздаёт
каждому устройству только его payload. Один общий шифротекст расшифровало бы
ровно одно устройство, а сервер бы этого не заметил: он не отличает шифротекст
от шума. Групповые сообщения — наоборот, один sender-key шифротекст на всех.

Устройство, для которого отправитель не зашифровал (например, оно
зарегистрировалось после выборки бандлов), **пропускается**, а не получает
пустой кадр: сообщение дойдёт после установки новой сессии.

## Вложения

```
K_blob = случайный AES-256 ключ (на каждый файл свой)
файл  -> чанки по 64 КиБ
чанк_i -> AES-256-GCM(K_blob, nonce_i, чанк_i, aad="frogster-attachment-chunk:i")
блоб   = конкатенация (nonce || тело || тег)
digest = SHA-256(блоб)
```

Индекс чанка входит в AAD, поэтому перестановка или пропуск чанка ломает
аутентификацию, а не даёт правдоподобный результат.

`{blob_id, K_blob, digest, size, mime, name}` едет получателям **внутри
Double Ratchet**. Загрузка несёт только шифротекст, размер и digest —
`content_hint` всегда обобщённый (`"attachment"`), поэтому сервер не знает, что
хранит: фотографию, документ или запись.

Digest проверяется **до** расшифровки: скармливать непроверенные байты шифру —
приглашение к атакам на выбранный шифротекст.

Проверено тестами: маркеры plaintext и magic-байты форматов (PNG, PDF) не
переживают загрузку; ключ не встречается ни в метаданных загрузки, ни в самом
шифротексте. В Go-тестах формат чанков реализован независимо от Dart — их
успешный round-trip кросс-валидирует wire-формат между двумя языками.

## Встречное открытие сессии

Оба собеседника могут открыть чат независимо, до прихода первого сообщения:
каждый жмёт «новый чат», каждый выполняет `establishOutboundSession` — и на
одну пару устройств возникают **две несвязанные сессии**.

Поэтому prekey-сообщение (`ct=1`) обрабатывается всегда, а не только когда
сессии нет. Условие «сессия уже есть — handshake игнорируем» приводило к тому,
что prekey-сообщение собеседника расшифровывалось *своей исходящей* сессией с
другими ключами: каждое сообщение падало по MAC, и ничто не указывало на
причину. Prekey-сообщение самодостаточно (несёт identity и ephemeral ключи),
поэтому построить по нему сессию безопасно всегда.

Чтобы не сбрасывать рэтчет посреди диалога — инициатор прикладывает handshake
к каждому сообщению, пока не получит ответ — сессия пересоздаётся только если
текущая **не может** расшифровать. Проверка идёт на копии состояния:
неудачная расшифровка на живой сессии продвинула бы рэтчет и сломала бы
следующее сообщение, превратив поправимое расхождение в мёртвый диалог.

Покрыто тестом `both sides opening a session independently still converge` в
`test/data/conversation_test.dart`; проверено мутацией.

## Верификация мутациями

Функциональные тесты не доказывают безопасность рэтчета: ошибка в нём не
ломает доставку. Поэтому в код вносились намеренные поломки, и проверялось,
что тесты их ловят.

### Double Ratchet (клиент)

| Мутация | Результат |
|---|---|
| Цепочка отправки не продвигается | поймана |
| `message_key == next_chain_key` (тихая потеря FS) | **изначально прошла**, добавлены тесты KDF |
| DH-рэтчет переиспользует пару ключей (нет PCS) | поймана |
| Отложенный ключ не удаляется (повтор) | **изначально прошла**, добавлен тест повтора вне очереди |
| Снята граница `maxSkip` (DoS) | **изначально прошла**, тест усилен проверкой сообщения об ошибке |
| Заголовок убран из AAD | **изначально прошла**, добавлен тест на поле, не влияющее на выбор ключа |
| Убрана привязка identity из AAD | **изначально прошла**, добавлен асимметричный тест |

### Sender keys (клиент)

| Мутация | Результат |
|---|---|
| Снята проверка эпохи (удалённый читает дальше) | поймана |
| Подпись не проверяется (подмена автора) | поймана |
| `message_key == next_chain_key` | **изначально прошла**, добавлены тесты KDF |
| Разрешён откат итерации (повтор) | поймана |
| Лишний ключевой материал в SKDM | **изначально прошла**, добавлен тест на состав полей |
| Снята граница пропуска (DoS) | поймана |

### Ротация эпох (сервер)

| Мутация | Результат |
|---|---|
| Эпоха не инкрементируется при удалении | поймана |
| Старые SKDM не удаляются | **изначально прошла**, добавлена прямая проверка таблицы |
| Принимается SKDM со старой эпохой | поймана |

Сейчас ловятся все 16. Это не заменяет внешний аудит перед продакшеном.

### Замечание о порядке проверок

Тест на границу пропуска в sender keys обнаружил реальную проблему: проверка
подписи стояла **до** проверки границы. Легитимный участник группы (умеющий
делать валидные подписи) мог бы заявить огромную итерацию и заставить вывести
произвольное число ключей. Порядок исправлен: дешёвые проверки границ идут
первыми.
