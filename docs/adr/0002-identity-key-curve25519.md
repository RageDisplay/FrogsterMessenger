# ADR 0002: Identity-ключ — Curve25519 + XEdDSA, а не Ed25519

**Статус**: принято
**Дата**: 2026-07-29

## Контекст

В исходном задании указан `crypto/ed25519` для генерации ключей.

X3DH требует выполнения Diffie-Hellman **с участием identity-ключа**:

```
DH1 = DH(IK_A, SPK_B)
DH2 = DH(EK_A, IK_B)
DH3 = DH(EK_A, SPK_B)
DH4 = DH(EK_A, OPK_B)        # опционально
SK  = HKDF-SHA256(0xFF*32 || DH1||DH2||DH3||DH4)
```

`DH1` и `DH2` используют identity-ключи обеих сторон. Ed25519 — подписной ключ
в форме Эдвардса; он не выполняет Diffie-Hellman напрямую. Следование букве
задания сделало бы X3DH нереализуемым.

Косвенное подтверждение: `libsignal_protocol_dart` объявляет `x25519` и
`ed25519_edwards` **разными** зависимостями — это разные формы кривой с разным
назначением.

## Решение

Устройство держит **две** identity-пары:

- **Curve25519** — только для Diffie-Hellman в X3DH;
- **Ed25519** — только для подписей (signed prekey, sender keys).

### Почему не XEdDSA одной парой, как в Signal

Signal использует одну пару Curve25519 и порождает Ed25519-совместимые подписи
через XEdDSA. Для этого нужна арифметика кривой Эдвардса (бирациональное
отображение u↔y плюс восстановление знака).

В `cryptography` 2.9.0 внутренности Ed25519 (`lib/src/dart/ed25519_impl.dart`)
**не экспортируются**, а `ed25519_edwards` 0.3.1 (MIT) объявляет
`sdk: >=2.12.0 <3.0.0` — то есть не поддерживается для Dart 3.12, хотя и
резолвится. Реализация XEdDSA потребовала бы писать арифметику кривой
самостоятельно.

Это ровно тот класс кода, которого ADR 0001 велит избегать: ошибка в
конверсии координат или обработке знака не приводит к падению, она тихо
порождает подделываемые подписи.

Две отдельные пары дают ту же гарантию, используя **только готовые проверенные
алгоритмы**. Так устроен MLS (RFC 9420) и большинство современных протоколов.

Цена: бандл ключей везёт два публичных ключа вместо одного (+33 байта), в
схеме БД появляется колонка `identity_key_ed25519`.

### Распределение по слоям

| Ключ | Алгоритм | Где живёт |
|---|---|---|
| Identity DH (клиент) | **Curve25519** | приватная часть — только устройство |
| Identity signing (клиент) | **Ed25519** | приватная часть — только устройство |
| Signed prekey | Curve25519, подпись Ed25519 | приватная часть — устройство |
| One-time prekey | Curve25519 | приватная часть — устройство |
| Подпись JWT | **Ed25519 (EdDSA)** | сервер |
| Аттестации устройств | **Ed25519** | сервер |
| Манифесты файловых блобов | **RSA** | сервер |

Таким образом `crypto/ed25519` из задания используется и на сервере (JWT), и на
клиенте (подписи). `crypto/rsa` не применяется на горячем пути сообщений: у
него нет forward secrecy.

## Последствия

- Схема БД хранит `identity_key_pub BYTEA` длиной ровно 33 байта (32 байта
  точки + однобайтовый префикс типа DJB). Ограничение зафиксировано в
  миграции через `CHECK (octet_length(identity_key_pub) = 33)`.
- Подпись signed prekey — ровно 64 байта, также с `CHECK`.
- Сервер может проверить самоподпись signed prekey как дешёвую проверку
  целостности от повреждённых загрузок. Это **не** доказательство владения
  приватным ключом — таковое невозможно по устройству протокола, и именно
  поэтому обязателен TOFU с safety numbers на клиенте (см. Этап 5).
