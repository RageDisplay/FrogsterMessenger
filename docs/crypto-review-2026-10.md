# Ревью криптослоя — октябрь 2026

Внутреннее ревью `client/lib/crypto/` перед выходом в прод. Сверялось со
спецификациями Signal ([X3DH](https://signal.org/docs/specifications/x3dh/),
[Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)) и с
тем, как код реально вызывается из `MessageRepository`.

Это **не** внешний аудит. Он по-прежнему нужен перед публичным запуском.

## Подробности

### 1. Нетранзакционная расшифровка Double Ratchet

`RatchetSession.decrypt` до проверки тега сдвигал receiving chain, складывал
пропущенные ключи и при новом ratchet-ключе в заголовке выполнял DH-шаг с
заменой root key. Если тег не сходился, изменения оставались.

Последствия:

- **Повторная доставка ломала переписку.** Дубликат уже расшифрованного
  сообщения расходовал ключ следующего, и следующее настоящее сообщение
  падало с MAC error навсегда. Ровно этот симптом описан в NOTES.md («после
  перезахода переписка рвётся»). Тогда исправили сервер, но клиент оставался
  хрупким.
- **Любой ретранслятор мог сломать сессию одним кадром.** Достаточно
  заголовка с произвольным ratchet-ключом: DH-шаг заменял root key ещё до
  проверки. Это под силу серверу, который по модели угроз не доверенный.

Исправление: снимок состояния перед расшифровкой и откат при любой ошибке.
Вытесненные пропущенные ключи затираются только при фиксации. Это требование
спецификации («if an exception is raised… discard any changes to the state»).

Тесты: `double_ratchet_test.dart`, группа «failed decrypts leave the session
intact».

### 2. Гонки при параллельной обработке

`MessageRepository` подписывался на кадры через `listen(_onEnvelope)` с
async-обработчиком, поэтому следующий кадр начинал обрабатываться на первом
`await` предыдущего. В `FrogsterCryptoEngine` не было сериализации по пиру,
а рэтчет делает `await` между чтением chain key и записью следующего.

Пачка сообщений из офлайн-очереди расшифровывалась одновременно на одной
сессии: один ключ выводился дважды, сдвиги терялись, появлялись MAC error.
То же при отправке, совпавшей с приёмом.

Исправление:

- в движке — очередь операций на каждого пира (`_serialized`): `encrypt`,
  `decrypt`, установка сессии и принятие смены ключа;
- в репозитории — `asyncMap`, то есть строго один кадр за раз, в порядке
  прихода.

Тесты: `crypto_engine_test.dart`, группа «concurrency».

### 3. Подпись sender key не покрывала шифротекст

Подписывались только метаданные (чат, эпоха, устройство, итерация). Каждый
участник группы знает chain key отправителя, значит может вывести его
message key и зашифровать что угодно. Подпись при этом оставалась бы
настоящей: участник при помощи сервера подменял бы содержимое чужого
сообщения.

В проде уязвимость не проявлялась: групповые чаты ещё не подключены к UI.
Исправлено до подключения: подпись покрывает метаданные и сериализованный
шифротекст.

Тест: «a member cannot swap content under the sender signature». Мутация
«подписывать только метаданные» им ловится.

### 4. Prekey-сообщение меняло состояние до аутентификации

`decrypt` для `ct=1` выполнял `establishInboundSession` до расшифровки:

- пиннил заявленный identity-ключ (при смене — плашка о смене ключа);
- заменял рабочую сессию и сохранял её;
- удалял одноразовый prekey.

Ни одно из этих действий ничем не подтверждено, пока сообщение не
расшифровано. Подделка от сервера давала ложную плашку о смене ключа,
сломанную переписку и сожжённые prekey.

Исправление:

1. Сначала пробуется существующая сессия; это безопасно благодаря п.1.
2. Затем строится сессия-кандидат и сообщение расшифровывается ею.
3. Пин, установка сессии и удаление OTPK выполняются только после успеха.
4. Неизвестный id одноразового prekey отклоняется сразу.

Тесты: группа «prekey messages are authenticated before they change state».

### 5. Sender key: нетранзакционная расшифровка, нет поддержки порядка

Цепочка сдвигалась до AEAD-проверки, а ключи пропущенных итераций
стирались. Сообщение, пришедшее не по порядку, терялось навсегда («behind the
chain»). Для групп это реально: сервер раздаёт сообщения по устройствам, а
офлайн-сброс может перемешаться с живой доставкой.

Исправление: вывод ключей во временные переменные с фиксацией после успеха,
хранилище пропущенных ключей (не больше 2000, каждый одноразовый) и
сериализация этого хранилища.

### 6. Signed prekey не ротировался

Ключ с `keyId: 1` жил вечно. Его приватная половина вскрывает первые
сообщения всех сессий, построенных на нём, поэтому компрометация устройства
задевала всю историю установок сессий.

Исправление в крипте:

- ротация раз в 7 дней, двухфазная (prepare → загрузка → commit);
- предыдущий ключ хранится один период;
- в prekey-сообщение добавлено поле `spk`, по которому получатель выбирает
  ключ;
- старые клиенты без `spk` получают текущий ключ.

Осталось: эндпоинт загрузки на сервере (`ReplaceSignedPreKey` в store уже
есть) и вызов из клиента — этапы 1.2/1.3.

### 7. Ключевой материал в SQLite открытым текстом

`ratchet_sessions.state` и `sender_keys.state` хранятся как JSON с chain
keys и пропущенными message keys. Комментарий в `session_dao.dart` полагается
на шифрование диска. На Windows без BitLocker файл в `%APPDATA%` читает любой
процесс пользователя, он же попадает в бэкапы. Тела сообщений лежат там же,
это задокументированный компромисс.

План: при миграции локальной БД v3 (этап 2) шифровать эти колонки
AES-256-GCM ключом из keychain, а заодно тела сообщений.

### 8. Повтор id одноразовых prekey

Каждый пул начинался со случайной базы в диапазоне 0..65535. Пулы по 100
ключей со временем пересекались. Новый приватный ключ перезаписывал старый с
тем же id, а сервер мог ещё выдавать старый публичный: сессия, построенная на
нём, не расшифровывалась.

Исправление: сохраняемый счётчик. Случайная только первая база, чтобы
переустановка вряд ли попала на занятые id.

### 9. Пин до проверки подписи

`establishOutboundSession` пиннил identity и при смене ключа удалял старую
сессию до того, как `x3dhInitiate` проверял подпись signed prekey. Бандл с
битой подписью отклонялся, но уже успевал запиннить ключ или снести сессию.
Порядок исправлен.

### 10. Ed25519-ключ вне TOFU

Пиннится и входит в safety number только Curve25519 identity-ключ. Ed25519,
которым подписан signed prekey, не пиннится. Сервер может подменить пару
«Ed25519 + SPK».

Конфиденциальность это не ломает: DH2 = DH(EK_A, IK_B) требует настоящего
приватного IK_B. Но подпись SPK теряет смысл, и сервер, знающий подставной
SPK, ослабляет forward secrecy первых сообщений.

План: добавить Ed25519-ключ в пин и в отпечаток safety number в этапе 2,
вместе с миграцией `pinned_identities`.

## Что проверено и в порядке

- X3DH: набор и порядок DH, домен-сепаратор `0xFF×32`, нулевая соль, AD =
  IK_A‖IK_B, проверка подписи SPK, отказ от all-zero DH (small-order точки).
- Double Ratchet: KDF_RK = HKDF(salt=RK, ikm=DH), KDF_CK с разными
  константами, заголовок в AD, лимиты `maxSkip`/хранилища, одноразовость
  отложенных ключей, затирание message key.
- AES-GCM: случайный 96-битный nonce. Каждый message key используется ровно
  один раз, так что риск повтора nonce несущественный.
- Вложения: свой ключ на файл, индекс чанка в AD, SHA-256 всего шифротекста
  проверяется до расшифровки. Обрезка хвоста ловится дайджестом из
  зашифрованного payload.
- Safety number: 5200 итераций SHA-512, сортировка отпечатков, версия
  формата.
- TOFU: `acceptedChange` сбрасывается после использования.
